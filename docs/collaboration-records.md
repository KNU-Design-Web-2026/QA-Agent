# 협업 기록과 성과 데이터 설계

KNUD Design QA Hub의 기록은 단순 버그 목록이 아니라 **배포된 화면을 기준으로 디자이너와 개발자가 어떻게 합의하고 개선했는지**를 남기는 근거다. 코멘트를 삭제하거나 상태만 덮어쓰지 않고, 중요한 변화는 이벤트로 보존한다.

## 남기는 데이터

| 알고 싶은 점 | 근거 데이터 |
| --- | --- |
| 어떤 화면에서 검토가 많이 일어났는가 | deployment, route, viewport, element `data-qa-id` |
| 어떤 문제가 반복되는가 | type, priority, annotation, 작성자 설명 |
| 피드백을 얼마나 빨리 반영하는가 | `created` → `in_progress` → `review_requested` → `done` 이벤트 시각 |
| 수정 후 다시 문제가 생기는가 | `reopened` 이벤트와 같은 element/route의 후속 코멘트 |
| 실제 배포 기반 QA였는가 | immutable deployment URL, Git SHA, 스크린샷, viewport/scroll |
| 협업 중 무엇을 결정했는가 | 상태 전환 note, 담당자, Figma 기준 링크, 감사 이벤트 |

## 보존 원칙

- `qa_comments`는 현재 상태를 빠르게 보여 주는 읽기 모델이다.
- `qa_events`는 생성·상태 전환·재오픈을 보존하는 append-only 이력이다.
- `audit_events`는 초대, 권한, 배포 등록 등 운영상 중요한 행위를 보존한다.
- 스크린샷은 Supabase Storage의 private bucket에 저장하고, DB에는 object key와 캡처 메타데이터만 저장한다.
- 완료 QA는 지우지 않고 `archived_at`으로 보관한다.

## MVP에서 바로 보는 지표

- 주차별 생성·완료 QA 수
- 유형별 비중: 시각/인터랙션/콘텐츠/디자인 기준 확인
- 우선순위별 처리 시간
- 완료까지의 평균 시간과 재오픈율
- 화면 경로·뷰포트·요소별 반복 코멘트 수

`qa_comment_metrics` view는 주차·유형·우선순위·상태별 건수와 평균 해결 시간을 제공한다. 정성적인 디자인 판단을 점수로 대체하지 않고, 회고에서 협업 방식을 개선하는 근거로 사용한다.

## 포트폴리오/회고 기록 문안

> KNUD Design QA Hub를 구축해 실제 Vercel 배포본을 디자이너가 직접 검수하고, 정확한 뷰포트·스크롤 위치·요소·스크린샷과 함께 피드백을 남길 수 있게 했다. 코멘트와 상태 전환을 데이터로 축적해 시각 QA의 반복 영역, 처리 리드타임, 재오픈 사례를 배포 단위로 추적했다. 이로써 Chromatic 중심의 개발자용 시각 회귀 확인을 보완하고, 디자이너와 개발자가 같은 실행 화면을 기준으로 빠르게 합의하는 협업 흐름을 만들었다.

실제 운영 데이터가 쌓인 뒤 검토 건수, 평균 해결 시간, 재오픈률 같은 수치로 보완한다. 데이터가 없는 효과 수치는 기록하지 않는다.
