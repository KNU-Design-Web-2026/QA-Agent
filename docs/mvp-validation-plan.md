# MVP 검증 계획: 배포 기반 Design QA

## 목적

KNUD Design QA Hub의 첫 검증 목표는 자동 시각 회귀 도구를 만드는 것이 아니다. **디자이너가 실제 배포된 KNUD 사이트에서 남긴 피드백을 개발자가 같은 실행 상태로 빠르게 재현하고 처리할 수 있는지**를 확인한다.

## 이번 MVP에 포함하는 범위

- Supabase 이메일 allowlist + 매직 링크 로그인
- 단일 KNUD 프로젝트와 Production deployment 선택
- 실제 배포 사이트 iframe 실행
- 1920 / 1350 / 1020 / 600 / 400px CSS viewport
- 핀·영역·화살표 코멘트
- deployment URL, Git SHA, 경로, viewport, scroll, `data-qa-id`, 좌표 저장
- 담당자와 상태 흐름: `열림 → 진행 중 → 검토 요청 → 완료`, 필요 시 재오픈
- 같은 실행 상태를 다시 여는 재현 링크
- 코멘트·상태 전환·재오픈의 협업 이력 저장

## 이번 MVP에서 제외하는 범위

- Render Playwright Worker와 자동 스크린샷 캡처
- Figma 이미지 오버레이와 pixel diff
- Slack/이메일 알림
- Agent 자동 분류·중복 병합·해결 판정

자동 캡처가 없더라도 코멘트의 배포 URL, Git SHA, 경로, 뷰포트, 스크롤, 요소 식별자, 정규화 좌표를 저장하면 개발자는 같은 배포본에서 문제 지점을 재현할 수 있다. 중요한 화면 증거가 필요한 경우에는 MVP 기간 동안 수동 이미지를 첨부한다.

## 성공 기준

개발자가 하나의 재현 링크로 아래 정보를 복원할 수 있으면 해당 QA는 재현 성공으로 본다.

```text
같은 배포본
+ 같은 경로와 query string
+ 같은 CSS viewport
+ 같은 scroll position
+ 같은 data-qa-id 요소
+ 같은 핀 또는 영역 위치
+ 코멘트, 담당자, 상태 이력
```

## 구현 순서

### 1. 접근과 데이터 연결

- Supabase 마이그레이션 적용
- 실제 협업자 4명의 이메일을 allowlist에 등록
- 매직 링크 로그인과 프로젝트 membership 확인
- Vercel의 KNUD deployment 환경 변수 확인

### 2. 실제 QA 기록

- 데모 UI의 코멘트 상태를 Supabase `qa_comments` 저장으로 교체
- 코멘트 생성 때 route, viewport, scroll, annotation geometry를 함께 저장
- KNUD 사이트에 최소 QA Bridge를 넣어 `data-qa-id`, 요소 rect, 현재 경로·스크롤을 전달
- 담당자 변경과 상태 전환을 `qa_events`로 기록

### 3. 재현 경험

- `/qa/[commentId]/reproduce`를 구현
- 저장된 deployment, route, viewport, scroll, annotation을 복원
- 대상 요소가 없거나 위치가 크게 바뀌면 “정확히 재현되지 않음”을 표시

## 실제 사용 테스트

기간은 2주를 권장한다. 디자이너와 개발자는 각자 최소 3건의 QA를 남기며, 서로 다른 페이지와 viewport를 포함한다.

| 역할 | 수행 시나리오 |
| --- | --- |
| 디자이너 | 시각 문제, 인터랙션 문제, 디자인 기준 확인을 각 1건 이상 작성 |
| 개발자 | 재현 링크로 화면 확인 후 담당자 설정, 진행 중, 검토 요청으로 전환 |
| 디자이너 | 검토 요청을 확인하고 완료하거나 재오픈 |

테스트에는 데스크톱 1개 이상과 모바일 viewport 1개 이상을 포함한다. 같은 문제를 두 명이 발견한 경우에도 별도로 남겨, 중복 판정이 실제로 필요한지 확인한다.

## 회고 지표

- 재현 링크로 문제 지점을 확인할 수 있었던 QA 비율
- 코멘트 생성부터 완료까지의 시간
- 재오픈 비율
- route·viewport·요소별 반복 코멘트 수
- 수동 이미지가 필요했던 사례 수
- 디자이너와 개발자가 기록한 사용 불편점

이 지표는 개인 성과를 평가하기 위한 점수가 아니라, 협업 흐름을 개선할 근거다.

## Render 자동 캡처 도입 기준

다음 중 하나가 2주 검증에서 반복될 때에만 Render Worker 도입을 검토한다.

- 저장한 재현 정보만으로 당시 문제 화면을 판단하기 어려운 사례가 반복됨
- hover, 메뉴 열림, 애니메이션처럼 일시 상태의 문제가 자주 발생함
- 수동 스크린샷 첨부가 QA 흐름을 방해함
- 재현 불가 QA가 전체의 의미 있는 비율을 차지함

근거가 없으면 Render는 도입하지 않는다. 비용이 드는 자동화보다 정확한 `data-qa-id`, 재현 링크, 간단한 코멘트 흐름을 먼저 완성한다.
